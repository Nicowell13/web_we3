# DOKU Checkout Integration

Use for DOKU Checkout popup, QRIS-only payment, or production checkout failures.

## Procedure

1. Read current DOKU Checkout backend and frontend integration docs; confirm payment endpoint, request fields, production/sandbox Jokul script URLs, and `loadJokulCheckout(paymentUrl)` popup flow before editing. Complete when planned payload and browser behavior match current docs.
2. Identify whether the failing request hit local or production backend before diagnosing it. Read the latest transaction and backend log, then reconstruct a redacted browser request, outbound DOKU URL/headers/body, exact provider response, and mapped application response; never expose bearer tokens, client IDs, secrets, digests, or signatures. State when dynamic headers were not logged rather than presenting reconstructed values as exact. Check callback URLs use the public frontend origin instead of an internal backend origin. Trace authentication and verify protected routes return `401` without a token rather than `500`; complete when request origin, upstream response, callback origin, and auth initialization are known.
3. When Bun loads `firebase-admin`, unwrap an ESM namespace with `module.default ?? module`, initialize once, and log initialization errors instead of swallowing them. Complete when Firebase Admin initializes on the production runtime and protected routes no longer fail before payment logic.
4. Initiate payment only on the backend; verify the current Checkout endpoint from DOKU's backend integration documentation before choosing `DOKU_CHECKOUT_PATH`, defaulting to the documented `/checkout/v1/payment` while allowing a merchant-proven override. Do not infer DOKU's upstream version from the application's `/api/v1/...` route or an older working project. Validate that the target starts with `/checkout/` and ends with `/payment`, then use that exact target for both the outbound URL and signature `Request-Target`. Build DOKU authentication from trimmed client ID and secret, a fresh UUID `Request-Id`, and `new Date().toISOString()` with milliseconds preserved. Serialize the final payload once and calculate its SHA-256 base64 digest. Send HTTP header `Digest: SHA-256=<base64>`, but build the HMAC component as `Digest:<base64>` without the `SHA-256=` prefix, matching DOKU's Non-SNAP signature documentation. Sign the newline-joined `Client-Id`, `Request-Id`, `Request-Timestamp`, `Request-Target`, and unprefixed `Digest` component, then send the exact serialized string as the request body. Add a unit test that separately verifies the prefixed HTTP header and unprefixed HMAC component against the documented target. Normalize both `DOKU_ENV=production` and `DOKU_ENV=live` to DOKU's production host, include order amount and invoice number, success/cancel callback URLs, and `payment.payment_method_types: ['QRIS']` when QRIS is the sole channel. Parse both observed Checkout response shapes: wrapped `response.payment.url` / `response.order.invoice_number` and top-level `payment.url` / `order.invoice_number`; read expiry from the matching payment object. Add one test for each shape. Treat a successful upstream response without a payment URL as a safe `502`, mark the transaction failed, and never let the frontend interpret it as success. Map upstream DOKU failures to a safe `502`, log the bounded provider response server-side, and mark the invoice-less local transaction failed. Complete when signature and response-mapping tests pass and the backend returns a non-empty DOKU payment URL without exposing secrets or leaving a pending orphan.
5. Keep the application's payment route version separate from DOKU's upstream Checkout version: call the mounted application endpoint (for example, `/api/v1/payment/create-link`) from every checkout entry point, including quick-order widgets, while the backend alone calls `DOKU_CHECKOUT_PATH`. Load DOKU's Jokul Checkout script in each entry point that can initiate payment, using the production CDN for production and sandbox CDN for sandbox. Preserve any local order-confirmation modal, then call `loadJokulCheckout(paymentUrl)` instead of opening a new browser tab; retain direct navigation only as fallback when the SDK is unavailable. For webhook verification, read the exact raw request body before JSON parsing and calculate its digest without reserializing parsed JSON; add a route-level test whose whitespace-sensitive body has a valid signature. Expose an authenticated, ownership-scoped transaction-status endpoint and poll it while the Jokul overlay is open; on `PAID`, `PROCESSING`, or `SUCCESS`, remove the injected overlay and navigate to the success view, and on `FAILED`, close it and show an error. Complete when a repository search finds no accidental application `/api/v2/payment/create-link` calls, checkout opens as an overlay, a real DOKU callback returns success instead of `401`, and the browser exits the overlay after the stored transaction status changes.
6. Trace fulfillment after payment through both callbacks: confirm DOKU webhook returns `200`, Digiflazz webhook returns `200`, and the stored transaction reaches `SUCCESS`. For products whose supplier response contains deliverable data such as a PLN token, persist both the supplier serial and parsed metadata, include those fields in the authenticated dashboard query, and render a copyable value in transaction history; complete when the user can retrieve the delivered value rather than seeing only `PROCESSING`.
7. Run the existing test suite and production build, deploy, restart backend/frontend services, and verify public health plus protected-route unauthenticated responses. When stale checkout code is suspected, delete the server `.next` directory, rebuild from scratch with production public environment values, then scan both source and `.next/server` for the expected `DOKU_CHECKOUT_PATH` and absence of the replaced path before restarting services. Complete when tests/build pass, services are active, health is OK, protected routes return `401` without credentials, and the runtime bundle contains only the intended DOKU checkout target.
