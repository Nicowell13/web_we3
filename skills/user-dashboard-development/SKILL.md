# User Dashboard Development

## Description
Procedure to add a user dashboard feature to the WebWe3 project, including backend service, routes, server integration, and Next.js UI with auth.

## Steps
1. **Create backend service & check-in loyalty**: Add `src/modules/dashboard/dashboard.service.ts` implementing `getDashboardData(userId)` to fetch profile, transactions, vouchers, and timeline. In `src/modules/checkin/checkin.service.ts`, award 0 points on days 1-4 of consecutive check-ins, batch-release 5 loyalty points only at every 5-day streak milestone (streak % 5 === 0), and reset streak on gap > 1 calendar day (WIB).
2. **Handle user avatar & Cloudinary**: Add `src/lib/cloudinary.ts` for image uploads and cleanup. Always validate MIME types and pre-convert images to optimized WebP buffers (256x256, quality 85) using `sharp` before sending to Cloudinary. On first login, fetch a DiceBear SVG using a random UUID seed, convert/upload it to Cloudinary with a `default_<uid>_<timestamp>` public ID, and persist the returned Cloudinary URL in Supabase `users.avatarUrl`; migrate empty or legacy external avatar URLs the same way during auth sync/dashboard load. Make dashboard and shared UI such as `Navbar` render the stored DB avatar, with an encoded UID DiceBear URL only as an immediate network-failure fallback. On manual avatar upload, upload the new image first, update the DB URL, then delete the previous Cloudinary image via `cloudinary.uploader.destroy`; never regenerate or delete the persisted default during refresh or check-in. Expose this through `POST /api/v1/user/avatar` in `src/modules/user/user.routes.ts`.
3. **Create backend routes**: Add `src/modules/dashboard/dashboard.routes.ts` exposing `/api/v1/dashboard` protected by `authenticate` and returning the data from the service.
4. **Integrate routes in server**: Import `dashboardRoutes` and `userRoutes` in `server/index.ts` and mount them with `.use()`.
5. **Create frontend tabbed page**: Add `src/app/dashboard/page.tsx` as a client component using `useAuth` to get ID token, fetch `/api/v1/dashboard`, and provide tabs: Overview/Profile, Transaction History, Activity Timeline, Loyalty & Vouchers, and Dynamic WhatsApp CS. Mask sensitive emails (e.g. `u***r@domain.com` or replace `@anon.wetri.com` fallback UIDs with verified account badges) to avoid info leakage, and keep avatar upload controls clean without verbose format disclaimers or noisy success banners.
6. **Ensure auth headers, RBAC, and file upload**: Call `user.getIdToken(true)` to force a fresh token on first login, pass `Authorization: Bearer <token>` for API requests, handle base64 image conversion for avatar uploads, and log non-2xx from `/api/auth/sync` instead of silent `catch(()=>void)`. Keep Firebase Auth as identity only; after `verifyIdToken()` succeeds, resolve authorization from Supabase Postgres `users.role` in `authenticate`/`requireRole`, ignore Firebase role/custom claims for admin access, and add a regression test where a forged Firebase `role: 'admin'` claim is rejected when the DB role is `user`. Ensure `src/db/index.ts`, `src/lib/firebase-admin.ts`, and `server/index.ts` load `.env.local` via `dotenv` at the top of the file (to prevent DB fallback to localhost:5432), load `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL`, `FIREBASE_PRIVATE_KEY` (replace `\\n` in private key), and URL-encode `%` in `DATABASE_URL` password as `%25` before `postgres()` connects.
7. **Secure admin routes & hidden dashboard**: Mount all admin backend endpoints under the obfuscated `/api/v1/old-school/*` prefix protected by `requireRole('admin')`, provide `GET /api/v1/old-school/ping` as an RBAC probe, and ensure legacy `/api/admin/*` paths return 404. Build the admin dashboard under the hidden frontend route `src/app/old-school/page.tsx` (never `/admin`), keep admin navigation out of public navigation menus, probe `/api/v1/old-school/ping` on load, and render a generic 404 not-found screen on HTTP 403 to avoid disclosing the admin portal surface to regular users.
8. **Run tests & build**: Run `bun test` with mocked auth token verification, and verify `next build` passes type checking.
9. **Verify dev runtime assets**: If Next dev returns 500 with React Client Manifest/module errors or reports a favicon conflict, remove duplicate route assets so only one `/favicon.ico` source remains (prefer `src/app/favicon.ico`), clear `.next`, restart `next dev`, and verify `/`, `/dashboard`, and `/favicon.ico` return 200.
10. **Add admin user enforcement**: For admin user-management features, add a DB-backed status enum with `active`, `suspended`, and `banned`, plus ban timestamp/reason fields. Enforce status in shared backend authentication before protected handlers run; expose admin-only list and status mutation routes under `/api/v1/old-school/*`, require a reason for bans, write audit entries for status changes, run `bun run db:push`, and test non-admin denial plus banned/suspended blocking.
11. **Close staged GitHub work**: Pull `main` before coding, implement one issue at a time, run `bun test` and `bun run build`, commit and push only requested source changes (exclude local `memory/`, `skills/`, and `tmp/`), then close the issue with commit and verification details.

12. **Add admin product catalog foundations**: For Digiflazz catalog management, extend `products` with supplier metadata (`brand`, `productType`, `supplierStatus`, `syncedAt`) and margin fields (`marginType`, `marginValue`), enforce uniqueness on `(supplierCode, supplierProductCode)`, keep supplier cost fields admin-only, and filter public catalog queries by both active product and active game. Push schema with `bun run db:push`, update schema regression tests, then run `bun test` and `bun run build` before committing.

13. **Sync supplier catalog safely**: Add an optional `getProducts()` capability to `TopUpProvider`, implement Digiflazz `POST /price-list` using its existing signing path, and expose an admin-only sync endpoint under `/api/v1/old-school/*`. Normalize supplier SKU/game identifiers, skip invalid or unknown-game rows, insert new rows inactive, and update only supplier-owned fields (`basePrice`, status, sync timestamp) for existing rows; preserve admin-managed selling price, activation, and margin. Return created/updated/unchanged/failed totals, mock supplier calls in tests, and report sync failures as controlled errors. Run `bun test` and `bun run build` before committing and closing the issue.

14. **Manage vouchers safely**: Keep admin voucher APIs under `/api/v1/old-school/vouchers`; validate and normalize all fields server-side, including `new_user`, `promo`, `loyalty_points`, and user-targeted `compensation`. Enforce active window, quota, prior orders, points, target user, and minimum purchase from DB data. Add and run tracked migrations before code reads new columns or enum values. Use left joins for transaction display metadata so catalog changes never hide history. After migration, run `getDashboardData()` against an existing production user and confirm transactions and points remain present; then run tests/build and commit only issue files.

15. **Expand hidden admin UI incrementally**: Extend `src/app/old-school/page.tsx` by loading admin products, vouchers, and users through existing RBAC APIs; provide sync, product enable/disable, voucher enable/disable, and ban/unban actions with visible success/failure feedback. For editable product fields, use controlled state, merge successful PATCH response into local list before authoritative reload, keep dialog open on failure, and display returned saved values. Keep non-admin generic 404 behavior, use stored API authority, run tests/build, commit only the page change, verify final Git status, and close the issue with commit details.

16. **Manage homepage promo banners from admin**: For homepage banner/promo updates, store editable fields in DB-backed `systemConfigs` keys, expose a public read route for homepage banner content, and expose admin-only routes under `/api/v1/old-school/*` for reading/updating text, CTA, active state, and image. Normalize saved config on read: trim text and image URLs, fall back when title/subtitle/CTA fields are blank, and verify production `GET /api/v1/home-banner` returns `isActive: true` before expecting the homepage hero to change. Upload banner images server-side to Cloudinary in a separate banner folder, persist the new URL before deleting the previous Cloudinary image, and render the homepage from the public banner route with hardcoded copy only as a fallback. Add a compact `/old-school` form for banner fields and image upload, then run `bun test` and `bun run build` before committing and closing the issue.

17. **Keep API-backed public Next pages build-safe**: When a public SSR page fetches a local backend API, mark it dynamic (`export const dynamic = 'force-dynamic'`) so production build does not require the development API to be running; then rerun `bun run build` and verify the route is listed as dynamic.

18. **Route frontend API requests to backend safely**: In server components, build absolute API URLs from `NEXT_PUBLIC_API_URL` with the development backend fallback (`http://localhost:3001`); browser components must use the same backend origin unless a verified Next proxy exists. Check `res.ok` before parsing JSON so HTML 404/500 responses do not become `Unexpected token '<'`. Keep public detail endpoints limited to public-safe fields rather than requiring an auth token unavailable to server-rendered public pages. Restart backend and frontend with a cleared `.next`, then verify list and detail URLs return 200.
